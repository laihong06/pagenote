# Project workflow

## Shared teaching and representation standards

Initial generation, knowledge-related revisions and direct explanations share `learning`, `representation`, `output`, `learner` and `profile`. Workflow modules govern preparation and safe edits, not separate teaching depth. Pure typo/symbol/format fixes stay within the requested scope. Keep workflow/intent routes, MCP module discovery, editable settings and exported prompt documentation in sync. Advertise only actual platform capabilities; do not invent native templates or substitute legacy HTML sandboxes for native Markdown S. See `docs/AI-REPRESENTATION-ROUTING.zh-CN.md`.

## Markdown S implementation

Founder correction: the primary Markdown S experience must use PageNote-owned renderers directly in the note DOM, with component state serialized into the current Markdown and persisted through existing autosave to the same project file. An iframe or embedded HTML document is not an equivalent implementation. Keep legacy HTML execution isolated only for compatibility; do not present it as the native product direction. Follow `docs/markdown-s/NATIVE-MARKDOWN.zh-CN.md` for this superseding requirement.

Render-engine PRs must include a separate real runtime screenshot for every advertised module (including SVG and Canvas), an exercised interaction with observable results, and the environment/source provenance. When the founder supplies a visual reference, render and inspect it, compare layout/typography/color/interaction against the implementation, explain concrete gaps and their causes, and improve them before resubmission. Do not use a single generic screenshot, static placeholders or design mockups as evidence for all engines. Show remaining visual differences candidly; do not declare aesthetic equivalence on the founder's behalf.

For Markdown S work, follow `docs/markdown-s/README.md`, `ARCHITECTURE.zh-CN.md`, `IMPLEMENTATION.zh-CN.md` and `ACCEPTANCE.zh-CN.md` in that directory. Preserve original Markdown, existing reading/editing/saving flows and unsupported-platform fallback. Declare the implementation milestone, affected platforms and acceptance case IDs in each PR; distinguish plans, unverified prototypes, verified functionality and published artifacts. Do not claim renderer safety, screenshot coverage or platform support without evidence. These feature-specific requirements do not override the founder-approved release policy or impose gates on unrelated future platforms.

## Pull request submission

Follow `docs/PR-STANDARD.zh-CN.md` and `.github/pull_request_template.md` for new or updated PRs. Explain affected modules, entry points, user actions, results and limitations in plain language. UI changes require real application screenshots for each affected platform, including before/after views and relevant interaction states; identify the environment and runtime commit. Design references do not replace runtime evidence. Explain screenshot exemptions for changes without UI impact. Maintainer visual review is separate from CI, functional checks and release approval. If GitHub does not auto-populate the template, copy it manually; do not assume a beta-only template is active on the default branch.

## Branch policy

Use `docs/BRANCHES.zh-CN.md` as the actual branch map: shared work targets beta; platform-private work targets that platform's existing beta. Platform root READMEs describe only that system; the shared root README is navigation. Retire completed task branches after preserving any unique commits, and retain stable history. Earlier migration fallback paragraphs below do not mean every platform-only change must keep targeting shared beta indefinitely.

The 2026-10-30 integration establishes independent desktop packaging entry points, platform version manifests, per-system documentation and platform validation CI. See `docs/INTEGRATION-2026-10-30.md` and `platforms/README.md` for actual implementation/validation status. Keep legacy runtime source paths compatible; moving a directory must not remove features. Consult the actual remote branches before routing a PR. Do not infer platform stable approval from creation of a branch or from the integration request.

The founder-approved multi-platform target workflow is specified in `docs/PLATFORM-MAINTENANCE.zh-CN.md`. Isolate platform implementations and maintain per-platform main/beta channels, version metadata, releases, READMEs, tutorials and screenshot coverage; trace shared-code synchronization and file-format compatibility. These are requirements for a staged migration, not a claim that migration is complete. Until a platform's source baselines, branches, build/version/release routing and documentation are established and verified in a migration PR, the existing root beta/main workflow below remains the actual submission route. Do not create stable platform baselines from unapproved beta code or rewrite published history. Platform updates must not bump or replace other platforms' releases. Every push still updates the root changelog; after platform logs exist, update the affected platform logs too. Explain documentation exemptions in PRs and keep original contributor PRs when requesting missing evidence.

`main` is the stable branch; `beta` is the integration and testing branch. Start all new features and routine fixes from `beta`; feature PRs must target `beta`. Do not push development changes directly to `main`. Promote tested changes through a PR to `main` only after real-use testing and explicit founder approval for that promotion. Passing CI alone does not authorize a stable release. Each branch has its own README and matching downloads: main links stable packages, beta links beta prereleases. Never use stable downloads as the beta download entry. Unavailable platform builds must be marked unavailable, not substituted with older builds. Beta packages use a distinct installation identity and user data directory and do not claim stable file associations. Preserve the appropriate branch README when promoting code.

Every push must include an accompanying `CHANGELOG.md` update describing the user-visible changes or fixes in that push. Keep unreleased work under the current Unreleased section and distinguish local builds from public releases. Do not push code or documentation changes without a matching log entry.

A source push is not a binary release. Before publishing a version, pass `npm run check:release`, build and test the matching artifacts, and publish installer/ZIP/source/checksums under the same tag. Update public README download links only with that release. Never reuse a published version for different binary contents.

After a release, advance package.json and package-lock.json to the next development version when changing runtime behavior. Keep README downloads pinned to the last published release until the next complete release is available.

Release decisions follow docs/RELEASE-POLICY.md. The founder-approved early-stage gates supersede historical exhaustive acceptance checklists. Windows v1.0 is approved based on LTH0001's Windows tests plus the founder's supplementary local tests; macOS stays experimental. Record non-blocking defects/unverified environments in KNOWN_ISSUES.md; do not add indefinite all-environment gates or claim unperformed tests.
