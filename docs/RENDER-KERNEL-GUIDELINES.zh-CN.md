# 渲染内核构建指导意见

> 范围：桌面端 `src/markdown.js`、`src/markdown-s.js`、`src/rich-editor.js`、`src/editing.js`、`src/main.js` 的 Markdown／Markdown S／PDF 渲染与批注投影，并兼顾 Android 的跨平台兼容约定。
>
> 与专项规范的关系：`docs/markdown-s/` 是可执行增强块的格式、权限、阶段和验收权威依据。本文件补充基础渲染内核与跨引擎共享机制，不另立 Markdown S 语法，不降低沙盒要求，也不把当前原型视为已验收能力。
>
> 性质：基于当前源码的静态架构评审与后续实施约束，不代表已经完成运行时性能测量。文中出现的性能问题均应先用真实文档和性能轨迹确认量级，再确定优化幅度。

## 一、总体判断

当前实现已经具备几个值得保留的基础：

- Markdown、公式、代码和 Mermaid 都在本地完成，Mermaid 按需加载，符合离线优先方向。
- DOMPurify 位于 Markdown HTML 和 Mermaid SVG 的提交边界，链接补充了 `noopener noreferrer`。
- 代码高亮失败保留源码，Mermaid 有加载、空内容和错误状态，单块失败不应拖垮整页。
- PDF 已有可见区域绘制、任务取消、文档 epoch 检查和 CSS 缩放期间保留文字层的意识。
- 富文本编辑仍以 Markdown 为持久化事实源，没有把渲染后的 HTML 当成主文档格式。

因此，**下一阶段不建议从更换 Marked、引入框架或重写整个编辑器开始**。真正需要补齐的是统一的渲染任务协议、块级更新边界、长文档资源预算和可观测性。先把“何时渲染、渲染谁、结果是否还能提交、失败如何降级”收敛为内核契约，再决定是否替换具体库。

## 二、目标架构：以文档块为中心，而不是以 DOM 操作顺序为中心

建议逐步形成以下单向管线：

```text
Markdown / PDF + revision
        ↓
纯函数规范化与解析（不改写源文件）
        ↓
带稳定 ID、源码区间和内容哈希的 RenderBlock[]
        ↓
策略、优先级、取消和资源预算
        ↓
HTML / KaTeX / Code / Mermaid / PDF 子渲染器
        ↓
generation 校验后的原子提交
        ↓
测量、缓存、滚动锚点与批注重投影
```

阅读和编辑可以共享解析器、子渲染器、主题令牌和安全策略，但应是两种不同的投影：

- **阅读投影**追求稳定、可选择、可复制、低内存和快速首屏。
- **编辑投影**追求选区连续、局部更新、撤销语义和 Markdown 往返一致。
- 不应为了复用而让阅读视图永远携带编辑控件，也不应让编辑控件进入序列化结果。

### 建议的最小任务上下文

项目目前使用 JavaScript，不要求为了这些类型立即迁移 TypeScript；先用 JSDoc 或等价对象约束即可。

```js
// 概念契约，不是要求照搬的 API。
{
  documentId,
  pageId,
  revision,       // 文档内容版本
  generation,     // 本次视图或块任务的代次
  signal,         // AbortSignal
  mode,           // read | edit | capture | prepare
  theme,
  viewportWidth,
  devicePixelRatio,
  resourcePolicy
}
```

每个异步块至少拥有：

```text
稳定块 ID + sourceHash + generation + state + sourceRange
state = idle | queued | rendering | ready | error | cancelled
```

关键原则：

1. **DOM 的 `dataset` 可以是状态镜像，不能成为唯一的任务真相。**
2. **提交结果前同时检查连接状态、块身份、sourceHash 和 generation。** 只比较源码无法防御 A→B→A 的旧任务回写。
3. **Markdown 源文档是唯一事实源，渲染 IR 和 DOM 都是可丢弃缓存。**
4. **一个块只有一个提交者。** 阅读重渲染、编辑装饰、截图准备和后台校验不能同时无序改写同一节点。

## 三、P0：先统一异步渲染的取消、优先级和提交规则

### 当前观察

`src/markdown.js` 使用模块级 `diagramQueue` 串行执行所有 Mermaid 任务，并通过 `isConnected` 和 `dataset.source` 避免部分旧结果提交。这是正确的安全意识，但还存在三类架构风险：

- 当前可见页面、历史预览、截图和后台页面准备共享队列，低优先级任务可能延迟用户正在等待的图表。
- 已经开始的 Mermaid 渲染不能由现有队列主动取消，超时等待也不会停止底层任务。
- 删除 `dataset.running` 后可为同一块再次排队；仅靠源码相等判断不能表达完整的任务代次。

`renderPage()` 对 PDF 已有 epoch 检查，可将这一思路推广为所有子渲染器共同遵守的协议，而不是各模块分别发明一套字段。

### 指导要求

1. 每个文档视图、页面和嵌入容器都有可销毁的 `RenderScope`；离开页面或替换文档时统一 `abort()`。
2. 每个块使用单调递增 generation；旧任务即使无法立刻停止，也不得提交、更新缓存或改变布局状态。
3. 全局串行只负责 Mermaid 引擎的并发安全，**不得兼任正确性机制**。
4. 调度优先级建议固定为：

```text
用户正在编辑的块
> 当前可见页
> 临近预取页
> 历史预览 / 导出截图
> 后台准备与非可见页
```

5. 队列需要支持出队取消、优先级抢占“尚未开始”的任务、单块超时和资源上限。无法安全中断的引擎任务仍须做 generation 隔离。
6. Mermaid 大图、超长源码和复杂公式必须有限额。限额触发时保留源码并显示明确状态，不能无限等待或静默空白。
7. 新能力先补竞争测试，再改实现：

- 图表源码 A→B→A，最后一次 B/A 任务先完成时仍只能显示当前代结果。
- 快速翻页、切文档、进入编辑、撤销和截图并发时，旧页不得回写新页。
- 一个图表失败或超时后，后续图表和正文仍可渲染。
- 销毁作用域后不得留下测量宿主、定时器、对象 URL 或事件监听器。

### Markdown S 的共享与隔离边界

当前 `src/markdown-s.js` 原型已经体现手动运行、CSP、opaque-origin iframe、源码 UTF-8 字节计量、运行 generation 和图表输入校验等正确方向，但专项文档已明确它尚未完成验收。后续应复用本文的 scope、generation、优先级和资源预算思路，同时严格遵守以下边界：

1. 本文的 `RenderBlock` 是对 Markdown S 块描述的调度扩展，不应另建一套与 `MarkdownSBlock` 竞争的格式模型；`protocol`、`engine`、`source` 和 `sourceRange` 保持语义一致。
2. 普通 Markdown 的 HTML 净化与 Markdown S 的脚本执行是两条权限路径。统一调度绝不等于普通 HTML 可以进入沙盒执行，也不等于增强块可以继承宿主任意权限。
3. Markdown S 继续使用专项规范的 `RendererAdapter` 责任、`idle → preparing → running → stopped` 状态、默认静止和同一视图最多运行 2 块的约束；本文通用异步块的 `queued/rendering/ready` 不替代产品运行状态。
4. 停止、换页、删除块、切项目和关闭窗口统一经过 `dispose()`。仅依赖根 DOM 被替换来表达生命周期不够明确，iframe、依赖加载、监听器、观察器、Object URL 和请求都要有可验证的清理归属。
5. 编辑和序列化必须还原原始围栏，工具栏、iframe、运行错误和注入依赖均不得进入 Markdown。组件源码保真以 Markdown S 的 F01–F06、E01–E07 为准，不用普通富文本回归替代。
6. 增强块的资源策略比普通 Markdown 更严格；普通附件或链接可用不代表沙盒内 fetch、远程图片、字体或模型可用。
7. iframe 是权限边界，不是 CPU、GPU 或内存的硬隔离。不得把当前 CSP／sandbox 组合宣传为能够安全执行任意不可信代码。
8. Markdown S 按 M1→M4 的专项阶段推进，不等待本文全部基础重构；共享机制成熟后增量替换原型内部实现即可。

## 四、P0：把富文本编辑从“每次输入处理整页”改为块级事务

### 当前观察

`src/rich-editor.js` 的输入处理会调用 `decorate()` 和 `emit()`：

- `decorate()` 扫描图表、公式、代码块和工具控件。
- `emit()` 对整棵编辑 DOM 执行 `htmlToMarkdown()`。
- 代码输入还会克隆片段、计算 Range 偏移、重建高亮 DOM 并恢复选区。

这套实现功能完整且已有回归测试，但长页输入成本随整页 DOM 和 Markdown 长度增长，应视为首要性能验证点，而不是只优化某个高亮正则。

### 指导要求

1. **输入事务只修改命中的块。** 普通段落输入不应重新装饰整页，也不应重建其他代码、公式和图表。
2. 将 `decorate()` 拆成可定位的 `mountBlock()` / `updateBlock()` / `unmountBlock()`；保留一个全量入口仅用于初次装载和必要的兼容恢复。
3. 渲染提交与持久化序列化解耦：

- 输入关键路径先维护内存中的块内容和脏标记。
- Markdown 序列化按短 debounce、块脏集合或空闲时段执行。
- 保存、翻页和退出前必须强制 flush，不能因延迟序列化丢失最新内容。

4. 代码高亮只处理活动代码块；连续输入时按帧合并，优先保证光标和输入响应。不得在每次按键时重复扫描无关节点。
5. 选区保存应以“块 ID＋文本偏移／路径”表达；异步高亮完成后，仅当块版本未变化才恢复选区。
6. `selectionchange` 监听器、对话框和根节点事件必须纳入编辑器生命周期，提供明确 `destroy()`。即使当前只创建一个实例，也不能让未来重建实例产生重复监听和全局 ID 冲突。
7. 继续保留 `contentEditable` 作为当前基线。只有当块级改造后仍无法通过选区、IME、粘贴和撤销验收时，才进行编辑器框架的隔离验证；不要一次性更换文档模型、编辑器和渲染器。

### 必须保持的编辑验收

- 中文 IME 组合输入期间不高亮、不重建活动节点、不丢选区。
- 撤销／重做保留源码语义，代码围栏长度、公式、Mermaid 和附件可往返。
- HTML 粘贴和 Markdown 粘贴走各自明确入口，sanitizer 与序列化白名单一致。
- 后台保存和异步图表完成不得移动当前光标。

## 五、P1：长文档采用“几何先行、内容按需、内存有预算”

### 当前观察

`src/main.js` 的 PDF 首屏初始化会顺序 `await pdf.getPage()` 获取全部页面尺寸；Markdown 文档会为全部页面立即执行 `renderMarkdown()`。滚动时 `paintVisible()` 和 `visiblePage()` 会遍历页面并读取几何信息。

PDF canvas 虽然已经按需绘制，但已绘制页面的 backing store 和文字层没有统一内存预算；高缩放、高 DPR 下也缺少像素上限。这些设计在页数较少时简单可靠，在长课件上则需要专门验证。

### 指导要求

1. 将“页面几何初始化”和“页面内容绘制”拆开。优先建立页尺寸缓存和累计偏移索引，首屏只等待当前页及定位所需信息。
2. 页面定位不要每次滚动线性读取所有 `getBoundingClientRect()`。使用缓存几何、前缀高度和二分查找；缓存失效必须可追踪。
3. 可见性预取以视口外一小段范围为界，不为全部 Markdown 页面提前启动 Mermaid、附件和嵌入内容。
4. PDF canvas 建立像素与字节预算，至少考虑：

```text
width × height × 4 bytes × device/zoom backing 因素 × 活跃页数
```

5. 远离视口的页面可按 LRU 释放重内容，保留轻量几何、页码和批注模型；回到页面时可重建。设置单页最大 backing 像素，超出时限制清晰度并给出可诊断状态，而不是分配失控。
6. 虚拟化不能只以“DOM 节点少了”为成功标准。必须同时验证文字选择、查找、页码定位、滚动锚点、批注重投影、截图和可访问性。
7. `content-visibility` 可作为测量后的局部优化，不要在未验证异步图表、锚点和截图语义前 blanket 应用到全部页面。

## 六、P1：把布局稳定作为渲染结果的一部分

Mermaid 当前以最小高度占位，完成后替换为实际 SVG。功能上可用，但异步内容完成时仍可能改变页高、当前页判定和批注位置。

建议将布局稳定纳入块契约：

1. 图像、图表和嵌入附件尽量在元数据阶段记录宽高比；已知尺寸直接进入缓存和占位。
2. 首次渲染使用合理骨架或源码占位，完成后若发生尺寸变化，由滚动锚点管理器统一补偿，而不是各子渲染器自行滚动。
3. 图表、公式和代码的错误态也必须是确定尺寸、可复制源码的合法渲染结果，不能作为异常跳出整页管线。
4. 字体加载、主题切换、容器宽度变化和 DPR 变化都应明确使哪些缓存失效，避免无差别全量重渲染。
5. 截图／导出应等待目标范围的稳定状态，而不是全局扫描并等待所有 `.mermaid-diagram`。超时必须返回可诊断的部分结果，并让底层任务按 scope 取消。
6. 临时测量宿主归具体 RenderScope 所有。现有页脚稳定性回归应保留，防止隐藏测量节点再次影响应用布局。

## 七、P1：统一安全、离线和资源策略，而不是散落白名单

建议引入显式 `RenderPolicy`，至少覆盖：

- HTML、SVG 和编辑器粘贴分别使用经过评审的 sanitizer 配置。
- 链接、图片、PDF、Markdown 嵌入的 scheme 和路径规则。
- 是否允许远程资源；桌面与 Android 若有差异，必须写成平台策略差异，不能依赖库默认行为。
- 单块源码长度、单页块数、递归嵌入深度、SVG 大小、并发数、超时和缓存容量。
- 附件请求的 AbortSignal、失败占位和敏感 URL 脱敏。
- capture／prepare 模式是否允许额外能力，不得因为隐藏 DOM 就绕过安全策略。

`validateNote()` 与真实渲染应尽量共享同一规范化和 token 语义，避免“校验通过但预览不同”或两套围栏／行内代码判断继续漂移。校验可以重解析，但不能私自采用另一套语法修复规则。

缓存键不能只包含源码。至少根据结果依赖纳入：渲染器版本、模式、主题、宽度档、DPR 档和安全策略版本。**不要跨策略复用已净化 HTML。**

## 八、P2：视觉系统以内容容器和渲染状态为中心

当前 `.prose`、Paper、Dark 和编辑器局部覆盖已能工作，后续不宜继续叠加越来越多的 `#preview` 特例。建议逐步收敛为：

1. **内容令牌**：正文、标题、次级文字、纸张、边框、代码背景、强调色、公式和错误色。
2. **组件变体**：`read` / `edit` / `capture` 明确区分，不让编辑工具样式污染阅读与导出。
3. **状态属性**：`data-state="loading|ready|error"` 比组合多个脆弱 class 更适合作为组件契约。
4. **容器优先**：双栏宽度是容器问题，优先容器查询或明确的宽度档，不根据整个窗口宽度推断笔记排版。
5. **Mermaid 主题显式化**：当前固定 `default` 主题和白底能保证可读性；若支持暗色／Paper 图表，必须将主题纳入任务与缓存键，不能只换外层 CSS。
6. **可访问性**：加载状态避免频繁 live-region 播报；错误可键盘展开；颜色对比、焦点、减少动画和 200% 缩放纳入验收。
7. **原文保真**：PDF 原文不应被阅读主题滤镜改变；Markdown 纸张和笔记可以使用主题，但批注投影必须使用同一坐标语义。

## 九、内核必须自带可观测性和性能门槛

没有数据时，不要以“感觉流畅”作为内核验收。建议开发模式提供轻量指标：

- 首屏当前页可交互时间。
- Markdown parse、sanitize、各类子渲染和 DOM commit 的分段耗时。
- 编辑器 input→下一次 paint 的延迟，以及整页 Markdown 序列化耗时。
- Mermaid 排队时间、执行时间、取消数和旧代提交拦截数。
- 异步内容导致的页高变化与滚动补偿次数。
- 活跃 PDF canvas 像素／估算字节、缓存命中和释放次数。
- 远程请求计数、未处理异常和超时块数。

可用以下作为首轮**建议预算**，再通过真实设备校准，而不是直接宣称为现有指标：

| 场景 | 建议验收方向 |
| --- | --- |
| 普通段落连续输入 | 关注 p95 input→paint，目标是不随无关节点数量明显增长 |
| 当前页单图首次渲染 | 正文先可用，图表不阻塞整页；完成后无意外跳页 |
| 200 页 PDF 打开与跳转 | 首屏不等待全页内容初始化；内存有上限且可回落 |
| 多公式、多图表长笔记 | 输入、滚动和后台渲染互不长期阻塞 |
| 快速翻页与编辑并发 | 旧代可见提交为 0，无游离宿主和未处理异常 |
| 离线／失败资源 | 外部请求符合策略，所有失败均有可读降级 |

## 十、测试金字塔：从“最终出现 SVG”升级为“渲染协议正确”

现有公式、代码、Mermaid 和页脚稳定性测试应继续保留，并补四层：

1. **纯函数契约**：规范化、语言别名、围栏、源码区间、URL 策略和错误分类。
2. **块级生命周期**：排队、取消、超时、A→B→A、销毁、缓存失效和失败隔离。
3. **真实浏览器交互**：IME、选区、撤销、粘贴、翻页、缩放、主题和批注重投影。
4. **视觉与性能基线**：真实课件、长中文、宽表格、复杂公式、大 Mermaid、缺图和损坏资源；既检查像素／几何，也记录耗时和资源。

跨平台建议共享一份带版本号的兼容语料与期望语义，而不是共享某个平台的 DOM 或截图。Android 的 69 页项目及 page 12 Mermaid 回归很适合作为语义语料来源；桌面和 Android 分别验证自己的真实渲染路径。

## 十一、推荐落地顺序

### 阶段 1：不加依赖，先补协议

- 为 Markdown 视图建立 RenderScope、块 generation 和统一取消。
- 将 Mermaid 队列改为支持优先级和出队取消，保留单引擎串行约束。
- 增加异步竞争、超时和销毁测试。
- 加分段性能标记，取得真实基线。

### 阶段 2：解决编辑关键路径

- 将全量 `decorate()` 拆为块级操作。
- 将整页序列化移出每次输入的同步关键路径，并保证强制 flush。
- 只更新活动代码块，补 IME 与选区压力测试。

### 阶段 3：治理长文档与内存

- 页几何缓存、可见页定位和预取范围统一。
- PDF backing store 预算与 LRU 回收。
- Markdown 非可见页延迟渲染，验证批注和截图语义。

### 阶段 4：根据证据决定是否深化 IR 或换库

- 如果校验、编辑、导出仍需要重复理解源码，再抽稳定 RenderBlock IR。
- 如果 Mermaid 主线程执行仍是明确瓶颈，再评估 Worker／独立沙箱，不提前引入复杂基础设施。
- 如果 contentEditable 在块级改造后仍无法通过核心编辑验收，再单独做编辑器框架 spike。

## 十二、评审禁区

- 不以引入框架、虚拟 DOM 或 Worker 的数量衡量内核先进性。
- 不把全部内容改为 canvas；文本选择、可访问性和编辑仍是一等能力。
- 不用“最终 DOM 看起来正确”掩盖旧任务回写、布局跳动和内存无上限。
- 不在没有真实 profile 的情况下先做复杂 AST、全量虚拟化或多层缓存。
- 不让阅读、编辑、截图和后台准备各自复制一套安全与语法规则。
- 不用源码字符串截断代替资源治理；截断必须是明确产品策略，并保留可诊断状态。

## 最终原则

**先保证“正确的块，在正确的作用域，以正确的代次提交”，再追求渲染速度；先让失败可读、资源有界、编辑局部化，再考虑更换引擎。**

对 pagenote 而言，优秀的渲染内核不是画出最多格式的内核，而是原文、笔记、批注和 AI 生成内容在翻页、编辑、缩放、离线与失败情况下仍保持一致语义的内核。
