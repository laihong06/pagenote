# 多平台源码、分支、版本与文档维护要求

本要求记录发起人于 2026-10-30 确认的管理方向：源码按平台划分边界，各平台独立维护稳定线、测试线、版本、文档和发布；共享能力保持可追溯同步。遵守既有 [发布政策](RELEASE-POLICY.md) 和 [PR 提交标准](PR-STANDARD.zh-CN.md)。

## 1. 当前状态与迁移边界

2026-10-30 状态修正：实际长期维护线、入口与缺口以[分支地图](BRANCHES.zh-CN.md)为准。各平台文档入口已建，源码边界和发布流水线仍为部分迁移；不能继续笼统说“什么都没有建立”，也不能说全部完成。根 README 只做项目导航；各系统界面、操作、功能和下载必须在对应系统 README 说明。

本文件是维护要求，不代表目录搬迁、平台分支、版本配置或发布流水线已经建成。迁移完成前，现有开发仍从 `beta` 开始，PR 仍指向 `beta`；不要让贡献者提交到尚不存在的目标分支。已有 `main`、`beta`、发布标签、下载和验收记录保持有效。

迁移必须在专门的 PR 中提供以下清单并逐项核验，再切换对应平台的提交入口：

- 记录该平台稳定／测试来源提交、已发布版本与制品，不能把未经批准的测试代码当成稳定基线。
- 建立平台目录与依赖边界，修正导入、资源、构建、测试、打包路径；不得只移动文件而不验证。
- 建立对应平台的稳定／测试分支、版本配置、发布入口与保护规则，更新维护指南中的实际目标分支。
- 验证稳定／测试安装身份、数据目录及文件关联隔离，保持历史数据与项目格式兼容。
- 补齐平台 README、教程、功能截图覆盖表和总导航；处理开放 PR 的目标分支与共享依赖。
- 记录迁移验证结果、未完成项和回退方式。平台迁移可分批进行，未迁移平台继续使用原入口。

## 2. 源码边界

目标组织如下；具体搬迁映射须在迁移 PR 中列出，不要求为了目录形式强行重写现有实现：

```text
shared/                   可直接复用的逻辑与公共格式约定
apps/desktop/common/      桌面共用逻辑
apps/desktop/windows/     Windows 系统适配
apps/desktop/macos/       macOS 系统适配
apps/desktop/linux/       实际启动 Linux 开发后建立
apps/android/             Android 独立实现，迁移现有 android/ 前须核验
apps/harmonyos/           实际启动鸿蒙开发后建立
docs/<platform>/          平台 README、教程、功能表、截图、更新日志
```

共享代码不得反向依赖某个平台的私有实现。Windows 的文件关联、Office 调用与 Mac 原生窗口等分别归属对应适配层。Android、鸿蒙可采用不同语言和原生界面，不强求源码复用。各平台共同遵守项目文件格式和兼容规则。

Linux、鸿蒙未真正启动实现时只在总览中注明规划状态，不创建空壳功能或宣称支持。现有 Android 实现不能因迁移计划被描述为“尚未开发”。

## 3. 分支与 PR 路由

迁移后的平台标识使用 `windows`、`macos`、`linux`、`android`、`harmonyos`。每个实际维护的平台使用 `<platform>/beta` 和 `<platform>/main`，不为尚未启动的平台预建稳定版。

| 改动类型 | 来源与目标 | 要求 |
| --- | --- | --- |
| 平台功能／常规修复 | 从该平台 beta 建立 `codex/<platform>-<topic>`，PR 回该平台 beta | 说明平台范围，更新对应文档与日志 |
| 共享代码／格式变更 | 先向共享集成线 `beta` 提交 PR | 提供受影响平台与兼容分析 |
| 共享变更同步 | 从目标平台 beta 建立同步分支，经 PR 合入 | 记录源提交、目标提交、冲突处理和验证结果 |
| 平台稳定晋级 | 该平台 beta 经 PR 晋级该平台 main | 实际使用测试及发起人针对该平台本次晋级的明确批准 |

根 `main` 保留现有稳定历史和总入口，根 `beta` 作为迁移期集成及后续共享集成入口；不得为搭建导航清空历史或把未验收平台代码晋级根 `main`。分支名代表仓库快照，不会自动隔离目录，必须同时遵守文件边界与审查规则。

平台之间不得随意整支互相合并；优先通过可审查的提交移植或等效补丁同步共享变更。不得直接强推稳定线或绕过 PR。晋级时保留稳定渠道 README，不能用 beta 文档与下载覆盖稳定入口。

## 4. 独立版本和独立发布

每个平台分别记录稳定版本、测试版本、开发版本、来源提交和制品。版本号不要求相同，发布时间不要求一致；Windows 更新不得自动增加 Mac 版本或替换 Mac 安装包。

目标版本配置按平台分别维护，例如 `platforms/windows/version.json`、`platforms/macos/version.json`。构建只读取选定平台的配置，确保应用内版本、安装包元数据、文件名、更新器和发布标签一致。不能只创建配置文件，却继续用公共 `package.json` 版本决定所有平台制品；迁移前仍遵守现有 `package.json`／锁文件一致规则。

新标签采用 `<platform>/v<version>`，例如 `windows/v1.2.0-beta.1`；示例不代表现有版本。历史标签不重命名、不复用。新标签正式启用前，必须同步修改现有标签触发器、版本校验和上传流程，不能假设原有 `v*` 流程会支持新命名。

只更新 Windows 的流程为：Windows 功能 PR → Windows beta → Windows 测试包 → 实际使用测试与明确批准 → Windows main 晋级 PR → Windows 正式制品。Mac 等其他平台保持原版本、原下载和原发布状态。

每次发布必须：

- 通过 `npm run check:release` 及迁移后对应平台的版本／发布检查；原命令需按平台适配时，先实现适配，不能无依据跳过。
- 构建和验证该平台所需的完整制品；安装包／便携包（适用时）、源码和校验清单对应同一标签及可追溯源码。不能混用其他提交的源码和二进制。
- 仅在完整发布后更新相应平台下载入口与总览版本状态；不可用架构明确写不可用。
- 不复用已发布版本替换不同二进制。发布后继续改运行行为时，将该平台配置推进到下一开发版本，README 仍指向最后完整发布版本。
- 稳定／测试使用独立安装身份与数据目录，测试版不争用稳定文件关联。

共享代码版本、软件版本和项目文件格式版本分别管理。格式变更须说明旧平台是否能读取新文件、是否可往返保存、迁移／备份与不兼容提示；不得默认其他平台会同步升级。

共享变更同步表至少记录：源 PR／提交、受影响平台、同步 PR／提交、验证结果、待同步或不适用原因。单个平台通过不代表全部平台通过。

## 5. README、教程与截图

根 README 是总项目入口：介绍整体用途、列出实际支持的平台与成熟度、各平台稳定／测试版本和对应文档／分支导航。没有建立的分支不可提供失效导航；开发版本、截图版本与已发布下载要明确区分。

每个平台单独维护 `docs/<platform>/README.md`，先说明整个 PageNote，再介绍本平台能力、安装、升级、限制、独立版本和渠道下载。平台分支的根 README 说明本分支身份并链接平台指南及总入口。稳定线只展示匹配的稳定下载，beta 只展示匹配的测试下载，不替换成旧包或其他平台包。

每个系统只有一个平台文档入口 README，链接到说明文件；“Windows 版／Mac 版”表示系统平台，“1.2.0”表示该系统的软件发行版本，不为每个发行版本复制整套平台入口。目录要求如下（以 Windows 为例，其他实际维护系统相同）：

```text
docs/windows/
  README.md                 本系统总览、渠道下载、教程与版本说明导航
  features.md               功能结构与截图覆盖表
  guide/
    README.md               配图教程入口，按模块链接操作说明
    reading.md              阅读教程，示例文件名
    notes.md                笔记教程，示例文件名
    images/                 教程配套真实截图，与教程一同维护
  CHANGELOG.md              按版本汇总变化，含 Unreleased
  releases/
    README.md               已发布版本索引
    <version>.md            每个发行版本的详细说明
```

以上是迁移目标，不代表示例文件或发布已经存在。教程与其截图位于同一 `guide/` 目录树，用相对 Markdown 图片链接直接展示，不与程序源码混放。首页用代表性截图展示整体，配图教程和功能覆盖表展示绝大部分乃至全部已实现的用户功能，不用一张无法阅读的长拼图代替。

平台 `CHANGELOG.md` 负责快速回答“每个版本更新了什么”；`releases/<version>.md` 详细记录该系统、渠道、发布日期、源码提交、增加／调整／修复内容、已知问题、升级与兼容提示、对应下载及校验入口。示例版本号不代表已经发布。开发工作先写 Unreleased，发布准备稿明确标记未发布；公开发布完成后再录入已发布索引。不得替换其他系统的说明或给未发布版本编造日期和下载。

功能覆盖表至少包含：模块／子功能、通俗用途、界面入口、操作步骤或教程链接、截图链接、可用状态／限制。逐项列出，未实现或仅有入口不能标为可用；没有界面的能力说明截图不适用原因。

截图须为对应平台的真实运行结果，注明软件版本、代码提交及环境，Markdown 可直接查看，资源路径可解析，不含私人材料。界面变化更新对应截图和教程；未改变的页面可以沿用并标注原版本，不伪装为新截图。遵循 PR 标准中的完整窗口、改前／改后和过程证据要求。

每次推送更新根 `CHANGELOG.md`，注明受影响平台及用户可见变化；迁移建立平台日志后同时更新对应日志。未发布工作放 Unreleased，区分本地构建、源码更新与公开发布。功能变化必须更新对应平台 README／教程／功能表；不需要更新时在 PR 中说明理由。

## 6. 审查和现有贡献者补充要求

PR 中必须有平台／渠道／目标分支、版本变化或不变理由、模块说明、文档更新、截图与测试证据、共享同步和文件兼容影响。界面美学审查、功能验证和发布批准分别记录，CI 通过不能替代维护者的布局审查或发起人的正式晋级批准。

重要分支应配置 PR、必要检查、禁止强推和删除等保护；按目录指定维护责任。检查按改动平台选择，共享改动覆盖受影响范围，必需检查必须能返回明确结论。截图对比用于发现变化，不能自动判定美观，也不能代替真实平台验证。

开放 PR 优先在原 PR 补充说明、提交和截图，不要求关闭后重复提交。多平台大型 PR 按平台和模块提供目录与证据；确需拆分时说明依赖和提交归属，保留原讨论记录。被后续 PR 覆盖的旧 PR 不要求重复准备整套材料，明确替代关系即可。

维护者提醒应逐项说明缺少什么，并提供当前可访问的规范与模板链接。缺截图或未验证如实标为待补；不得凭本规范宣称已有 CI 强制检查、分支保护或发布能力已经部署。非阻断缺陷和未验证环境按既有政策记录，不增加无限期全环境门槛。
