# Mac 雨课堂接入可行性验证

日期：2026-10-22（Asia/Shanghai）

状态：独立试验完成；网页会话采集、标准项目导入与离线 OCR 已实测。产品内置雨课堂登录、课程发现与持续同步尚未实现。

用户随后明确要求登录完全内置于 pagenote。下述 Edge 试验保留为历史事实，仅证明导入和解析可行，不满足 [应用内登录与实时采集需求](requirements.md)。

## 本轮目的

响应“先尝试 Mac 能不能接入”，用一份真实可访问课件验证最短路径，不将一次性采集工具作为产品实现交付，也不扩大到其他平台验收。

## 已执行操作

1. 使用用户 Mac 上已登录的 Edge 雨课堂标签页读取一份既有课后报告。原标签页保持原位置；另建临时标签页进入报告内的课件页面。
2. 尝试直接打开源码中出现的课程列表 GET 接口。页面返回未预期的短 JSON 对象，而非课程列表；本次未确认原因，不能据此声称原生 HTTP 课程发现已通过。
3. 报告时间线有重复播放的页面；改从课后总览打开完整课件。选择的一份课件显示 82 页，按页面标签取得 P1 至 P82 的顺序。
4. 页面图片采用懒加载，存在 1x1 占位图；完成实际图片加载后，核对全部 82 张原图均为 1280x960 JPEG，82 个资源标识互不重复。
5. 通过浏览器资源导出能力一次批量保存 82 张课件图片：请求 82，成功 82，失败 0；完整比较导出资源顺序与 DOM 页序一致。
6. 用临时脚本按原始 JPEG 合成 82 页 PDF，并生成兼容 v1 的 `project.pagenote`、独立空白分页笔记、原始图片和不含认证参数的试验来源清单。产物存放在仓库之外的本机文稿目录。
7. 执行 `npm run package:mac:local`，重新构建并打包 arm64 应用。检查 `app.asar` 时间晚于所核对的 175 个项目运行输入；确认从 `release/mac-arm64/pagenote.app` 启动。
8. 应用启动时恢复了用户原有文档；随后通过原生“文件 -> 打开项目”选择新建的试验项目。应用状态确认当前页 1、总页数 82、PDF 模式。
9. 通过实际应用的页面准备工具对第 2 页执行自动 OCR：Guten OCR 1.4.9 / PP-OCRv4，完成 12 个文字块、122 个字符，报告的低置信度块数为 0；第二次读取命中缓存。
10. 检查应用生成的第 1 页工作区截图与第 82 页截图，封面和结尾均正常。检查试验项目的 JSON / Markdown / manifest，未发现 Cookie、Authorization 或带签名参数的下载链接。
11. 通过正常保存与退出关闭应用，确认固定入口的主进程已经退出，再重新打开同一个 arm64 应用；原生界面恢复新建课件，显示当前页 1、总页数 82。

本次使用的单次脚本位于系统临时目录，不属于产品模块。没有运行候选第三方项目的入口，没有执行签到、作答或课堂实时连接，也没有调用云端模型。未修改用户原有项目的正文或笔记。

## 后续实现依据

- Mac 的“已授权网页课件 -> 本机资源 -> 标准项目 -> PDF 阅读 / 离线 OCR”链路具备实测依据。
- 在 pagenote 自身的 Electron 登录窗口和独立会话中验证官方登录与请求头需求；如需网页兼容采集，也只使用应用内上下文。Edge 试验不是产品登录后备方案，不能把 Edge 登录成功等同于 pagenote 自身登录成功。
- 原生课程列表和课件接口需要记录实际请求/响应契约，才能判断本次直接导航返回异常结构的原因；不能仅凭开源路径猜测字段或认定接口失效。
- 后续产品实现继续遵守 [公共调研](research.md) 的跨端来源、更新、凭据隔离和既有笔记保护约定。
