# PR 提交与界面审查标准

本标准适用于后续新增或更新的 PR，帮助维护者看懂功能结构，并通过真实截图判断界面是否简洁。新功能和常规修复提交到 `beta`；正式版晋级仍遵守 [发布政策](RELEASE-POLICY.md)。

同时遵守 [多平台维护要求](PLATFORM-MAINTENANCE.zh-CN.md)：平台源码边界、平台 main/beta、独立版本与发布、共享同步、README／教程／功能截图覆盖都属于提交要求。平台分支迁移尚未完成时，仍向现有 `beta` 提交，不要求改投不存在的分支。每个 PR 明确实际路由与迁移状态。

## 1. 先让人看懂改了什么

PR 开头用日常语言说明：谁在什么场景遇到什么问题，这次操作前后有什么变化。不要只写“优化体验”“完成模块移植”或粘贴提交记录。

例如：“阅读课件时，原来需要打开数字输入框才能跳页；现在点击右上角页码就能看到缩略图，点击缩略图跳转，关闭后继续阅读。”

说明受影响的平台，以及哪些行为跨平台一致、哪些布局因触控、鼠标或窗口大小而不同。没有改动的平台写明“未改动”，不要用一个平台的截图代表另一个平台。

## 2. 功能结构要完整、通俗

列出本次涉及的功能模块与子功能，交代它们在应用中的位置和相互关系。大型 PR 按模块分组，提供目录或文档锚点；不要把多个独立改动藏在“其他优化”里。

每个模块填写下表；有多个入口或重要子功能时，分行说明。

| 模块／子功能 | 用来做什么 | 从哪里打开 | 用户怎么操作 | 操作后发生什么 | 怎样退出／撤销 | 与其他模块的关系及限制 |
| --- | --- | --- | --- | --- | --- | --- |
| 页面预览 | 快速找到想读的课件页 | 阅读器右上角页码 | 打开预览，点击缩略图 | 跳到目标页，显示当前页位置 | 关闭预览继续阅读 | 跳页前保存当前笔记；预览加载失败时显示提示 |

写作要求：

- 名称与实际界面一致；图标按钮也写出含义。内部类名和文件名放在后面的技术说明中。
- 第一次出现专业词时解释含义。例如“信息素矩阵”应解释成“记录每条边受推荐程度的表”，不能假设维护者知道术语。
- 说明必要的权限、联网条件、保存位置、失败提示，以及切页或关闭时未保存内容如何处理；不相关的项目可写“不适用”。
- 明确新增、替换、移动、删除的入口，避免用户升级后找不到功能。
- 未完成、仅预留入口、尚未接通的功能必须直说，不得与可用功能混写。

## 3. 界面改动必须提供真实截图

影响界面布局、文案、图标、颜色、主题或交互状态的 PR，进入正式审查前必须有可直接查看的截图。缺少证据时可以先开 Draft，并列出待补项。

截图要求：

- 每个受影响的平台分别提交运行中的应用截图。模拟器可用于 Android；macOS 使用实际 macOS 应用。HTML 参考稿、设计图和生成图片只能作为设计参考，不能替代运行截图。
- 现有界面提供改前／改后对照，尽量使用同一份示例材料、同一页面和相同尺寸。新增界面没有改前截图时注明原因。
- 至少有一张完整应用窗口或屏幕图，便于判断整体空间分配；局部图用于补充，不得仅提供裁剪细节。
- 展示本次改动涉及的主要页面、展开面板或弹窗，以及关键状态。例如修改编辑器时展示键盘展开后的布局；修改工具栏时展示工具展开后是否遮挡正文。
- 窗口缩放、横竖屏或明暗主题受到本次修改影响时，补充对应状态；无需为无关平台和状态重复截图。
- 使用公开或合成示例材料，移除账号、密钥和私人笔记。保留正常比例与清晰文字，不用美化、重排版或拼接伪造运行效果。
- 图片直接嵌入 PR 描述，或链接到仓库中可直接查看的图片。不要只提供需要下载解压的压缩包。

每组截图注明：平台、系统版本、设备／模拟器、窗口或屏幕尺寸、缩放／显示密度、主题、截图对应的运行代码提交 SHA。截图之后若只改文档或证据，可沿用并注明；若相关界面代码变化，必须更新截图。无权限截取的平台写“待补”，不能声明已通过。

涉及展开、切换、拖动、翻页等过程时，再提供一段简短连续录屏，或按顺序编号的操作截图，说明每一步动作和结果。

## 4. 简洁性和美学怎么审

维护者依据截图和操作证据逐项判断，并给出“可接受／需要调整／证据不足”。不是按个人喜欢的颜色打分，也不要求各平台界面完全一样。

| 审查项 | 看什么 |
| --- | --- |
| 内容优先 | 课件和笔记是否占据主要空间；工具是否长期挤占阅读区或遮挡正在编辑的内容 |
| 入口清楚 | 常用操作是否容易找到；图标是否能理解；当前阅读、编辑或书写状态是否明确 |
| 按需展开 | 次要操作是否集中到菜单或上下文面板；是否增加了重复入口或常驻工具条 |
| 层级克制 | 主次按钮、标题和正文是否清晰；颜色、边框、阴影是否承担明确作用 |
| 排版一致 | 对齐、间距、图标尺寸和文字风格是否一致；是否有挤压、截断或无意义的大块留白 |
| 易读易操作 | 文字和图标是否清晰、对比是否足够；触控目标是否容易点击；焦点和选中状态是否可辨认 |
| 状态可理解 | 加载、失败、空内容和保存反馈是否清楚；关闭或返回是否方便 |

若增加常驻按钮、工具栏或面板，说明为什么必须常驻，以及为什么不适合放进已有菜单。若采用新视觉风格，解释与现有界面如何保持一致。

维护者确认本次界面“可接受”后，才视为通过布局审查。CI 通过或代码可合并不能代替这一步；这也不等于批准正式发布。非阻断的小问题可记录为后续事项，不追加无限期的全平台验收要求。

## 5. 测试证据与审查顺序

1. 检查问题说明和功能结构，确认范围清楚、没有重复 PR 或隐含依赖。
2. 查看截图和操作证据，先判断布局与功能组织；不合理时先调整，避免完成大量代码后才发现方向有误。
3. 核对与改动相关的测试，记录命令、平台、结果，以及失败、跳过和未验证范围。区分贡献者自测、CI 和维护者复核。
4. 核对 `CHANGELOG.md`、目标分支、保存兼容性及已知问题，再决定是否合并到 `beta`。

不涉及用户界面的纯文档、内部重构或构建修复，可以不附界面截图，但必须说明不适用的原因。纯文档 PR 可以写“无运行功能模块”，并用通俗语言解释读者和工作流程的变化。涉及用户可见结果的改动不能仅以“后端修改”为由免除必要的结果说明。

## 6. 模板与生效范围

提交时使用 [PR 模板](../.github/pull_request_template.md)。如果 GitHub 未自动带出模板，请手动复制；模板的自动加载受 GitHub 默认分支配置影响，本标准进入 `beta` 不代表已同步到 `main`。

已有 PR 后续更新时，补充与本次更新相关的结构说明和界面证据，不要求伪造历史截图。布局审查、功能测试和正式发布是不同的决策，按实际证据分别记录。

## 7. 平台版本与文档必填项

- 列出每个受影响平台、渠道、实际目标分支、软件版本是否变化；只改一个平台时明确其他平台版本和制品保持不变。
- 共享改动列出来源、同步去向、验证结果及待同步平台；涉及项目格式时补充跨版本读写兼容说明。
- 提供对应平台 README、配图教程和功能覆盖表的变更链接。覆盖表逐项关联已实现功能、入口、操作和真实截图；不以“测试已通过”替代功能说明。
- 更新根日志及已建立的平台日志，区分未发布源码、本地包与公开发布；未完整发布不得提前改下载入口。
- 已有 PR 直接编辑描述和补充提交，无需重新开重复 PR。被后续 PR 包含的旧 PR 只说明替代关系，证据优先集中在实际集成 PR。
